Raw transcript of the live run behind ADR-0012 and the claim in section 9 that latched diagnoses
and open cases survive a restart. The unit tests prove the round trip against a filesystem; this
is the only record of it happening in a deployed container.

# 1. A document appears before anything has latched
~5 s after start, project/storage/fault-monitor/state.json, 156 bytes:
  cases                []
  believedFanSpeed     0.7
  believedPositions    all six zones at 0.15
  unresponsiveDampers  []
The empty-case document is written on the ordinary cycle, not only when something is wrong. That
is deliberate: the believed positions and the believed fan speed are state whether or not a fault
is open, and they are the belief AhuFlowModel.java:147-155 says a restart would otherwise reset to
nominal and keep wrong for hours.

The two services agree on the case id without ever having exchanged it as state. Each derived it
from the same FaultStateChanged on the wire, which is the cross-check worth noticing: the
documents are two independent recordings of one episode, not one document copied.

# 3. The kill, which is a SIGKILL and not a graceful stop
docker kill ventilation-fault-detection-fault-monitor-1
docker compose ... start fault-monitor
  StartedAt   2026-10-10T22:34:01.567708713Z
  RestartCount 0

RestartCount is 0 for the same reason T-27 records: a kill issued through the daemon is a manual
stop, so the restart policy is not what brought it back. That is the point here — nothing about
this result depends on the restart policy, only on what was on the volume.

# 4. After the restart
fault-monitor startup line, 22:34:02, simulated 2026-10-09T10:31:19Z:
  ... latched diagnoses survive, on /state/state.json a restart

project/storage/fault-monitor/state.json, after the restart and several further cycles:
  case id        779b28fb-78f4-43a7-9fe0-db4dd787bbeb   (UNCHANGED)
  state          COMPENSATING
  classification STUCK_DAMPER
  confirmedAt    2026-10-09T10:09:00.798175500Z          (UNCHANGED)
  updatedAt      2026-10-09T11:02:00.391167840Z          (ADVANCING)
  unresponsiveDampers ["A115"], believedPositions A115 = 0.15

That combination is what makes this conclusive rather than suggestive. A monitor that had started
cold would have re-detected the fault from scratch and produced a NEW case id and a NEW
confirmedAt, because both are minted at confirmation; it would also have had to pass back through
WARMUP and SUSPECT first. The id and the confirmation instant are identical across the kill while
updatedAt keeps moving, so the case that is running after the restart is the same object that was
running before it, still live.

# 5. Atomic write
No .pending file in either directory at any point after a write completed. The document is written
to <name>.pending in the same directory and renamed over the target with ATOMIC_MOVE, so a process
that dies mid-write leaves the previous whole document rather than a truncated one.

# 6. What this run does NOT show
- The supervisor was not itself killed in this run. Its document was verified present and correct
  across the monitor's restart; its own recovery path is covered by its unit tests.
- The journal on this host carries rows from earlier demo runs at the same START_AT, so simulated
  timestamps in `decisions` are not unique to one run. Every assertion above is read from the
  state documents and the container metadata instead, which are per-run.
- A cold start was not forced by deleting the document, so the "missing document means cold start"
  path is covered by unit tests only.
